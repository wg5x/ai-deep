# 沟通通道借力评估

> 日期：2026-06-07
> 状态：建议稿
> 结论：暂不自研飞书或微信接入。先用现成工具验证“AI 能否主动、低打扰地找用户确认”。

## 1. 背景

用户要的不是一个聊天系统，而是副业型协作通道：

```text
AI 平时静默推进
→ 真需要用户判断时主动通知
→ 用户用很短的回复确认
→ AI 继续推进或暂停
```

这件事本身是项目原则的考核：

```text
能不能借力？
能不能小步验证？
能不能低成本掉头？
```

因此，通道建设不能默认进入自研开发。

## 2. 本次判断

当前不建议做：

- 自研飞书 webhook 发送脚本
- 自研微信机器人
- 自研多轮对话系统
- 自研通知后台

建议先做：

```text
人工 + 现成工具 + 明确协议
```

第一版只验证一个问题：

```text
当 AI 有 P0 决策点时，用户能不能在非盯屏状态下收到并用数字回复？
```

如果这个问题还没有被证明，就不应该继续做更复杂的集成。

## 3. 借力候选

| 方案 | 借力对象 | 优点 | 风险 | 当前判断 |
|---|---|---|---|---|
| Codex 线程 + 固定查看 | 现有工作环境 | 零接入、零账号、零外部风险 | 不主动触达用户 | 作为备份通道 |
| 飞书群 + 人工转发 | 飞书现有群聊 | 最低成本验证通知文案和回复协议 | 需要人工复制消息 | 推荐先试 |
| 飞书自定义机器人 | 飞书现成 webhook | 适合结构化群通知 | 仍需要 webhook 和安全配置 | 可作为第二步 |
| Apprise | 开源通知聚合器 | 支持 Lark/Feishu、PushDeer、Gotify 等多通道 | 仍需安装/配置，不解决用户回复自动读取 | 值得优先评估 |
| ntfy | 开源推送服务 | HTTP PUT/POST 即可推到手机/桌面 | 公开 topic 需注意隐私；用户体验未必适合日常微信习惯 | 可做快速试验 |
| Gotify | 开源自托管通知服务 | 有 Web UI、REST API、Android 客户端 | 需要自托管，iOS/微信日常触达弱 | 暂缓 |
| PushDeer | 现成/开源推送工具 | 面向个人推送，接入轻 | 需要用户安装/配置，微信触达并非无成本 | 可选 |
| WxPusher / Server 酱 | 微信生态推送服务 | 更接近用户日常微信 | 第三方依赖、账号/服务稳定性需评估 | 谨慎试，不作为默认 |
| Wechaty | 开源聊天机器人框架 | 可做真正微信/IM bot | 维护成本、账号风险、复杂度高 | 当前不做 |
| n8n | 现成自动化平台 | 可视化连接 webhook、HTTP、定时任务 | 引入平台和运维复杂度 | 后续有多个自动化再考虑 |

## 4. 推荐路径

### 第 0 步：不开发，只验证协议

执行方式：

```text
AI 在 Codex 线程生成 P0 通知
→ 用户手动确认是否清晰
→ 记录用户是否愿意按数字回复
```

通过标准：

- 用户不需要读长文
- 用户能在 30 秒内判断回复
- AI 能根据数字继续推进或暂停

### 第 1 步：飞书群人工转发

执行方式：

```text
AI 生成 P0/P1 文案
→ 人工复制到飞书群
→ 用户在飞书回复数字
→ AI 手工记录结果
```

这一步仍然不需要开发。

通过标准：

- 用户能收到提醒
- 用户愿意在飞书处理
- 数字回复足够用
- 没有明显打扰感

### 第 2 步：优先试 Apprise，而不是自研

如果第 1 步有效，再评估 Apprise：

```text
一条通知接口
→ 可切换飞书、PushDeer、Gotify、其他通道
→ 降低未来换通道成本
```

只有当 Apprise 或现成平台卡住，并且通知通道已经证明有价值时，才考虑写少量适配代码。

## 5. 明确拒绝项

当前拒绝：

- 个人微信自动化
- 模拟微信客户端
- 长期运行的微信 bot
- 为通知功能自建后台
- 为一次测试引入复杂 n8n 流程
- 还没验证回复协议就做消息接收自动化

理由：

```text
这些动作会把一个小通道变成基础设施项目。
这不符合简单、持久、挣钱。
```

## 6. 是否做飞书开发

当前判断：

```text
不做。
```

更准确地说：

```text
不在当前阶段自研飞书接入。
```

原因：

- 通道价值还没有验证。
- 飞书已有自定义机器人和开源通知工具可借力。
- 用户没有要求开发接入。
- 自研会制造维护面，而不是直接验证现金流。

## 7. 需要用户做什么

当前只需要用户判断一件事：

```text
是否愿意先用飞书群人工转发，测试 3 条 P0/P1 通知？
```

可选回复：

```text
1 可以，先人工转发测试
2 不用飞书，继续只在 Codex 线程里看
3 我想试微信生态推送
4 先不做通知通道
```

## 8. 后续触发条件

只有同时满足以下条件，才进入技术接入：

- 人工转发验证有效
- 用户确认飞书或某个通道值得保留
- 每周至少出现 2 次以上需要异步确认的场景
- 手工复制已经明显影响推进效率
- 有现成工具无法覆盖的明确缺口
